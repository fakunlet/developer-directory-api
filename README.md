# Developer Directory API

A REST API for managing a directory of developers — their name, tech stack, and
years of experience. Built as a layered Spring Boot application (controller →
service → repository) backed by PostgreSQL running in Docker.

Every response shown in this README was captured from a real run against a live
Postgres container.

## Tech Stack

| Component | Version / Notes |
| --- | --- |
| Java | 17+ (developed on JDK 23) |
| Spring Boot | 3.4.1 |
| Spring Web | REST controllers |
| Spring Data JPA | Hibernate 6, `JpaRepository` |
| Bean Validation | Hibernate Validator, request body constraints |
| PostgreSQL | 16 (via Docker) |
| Testing | JUnit 5, Mockito, MockMvc, AssertJ — 18 tests |
| Build | Maven |
| Containers | Docker + Docker Compose |

## Setup

### 1. Start PostgreSQL

From the project root:

```bash
docker compose up -d
```

Confirm it's healthy before starting the app:

```bash
docker compose ps
```

```
NAME                     IMAGE         STATUS                   PORTS
developer-directory-db   postgres:16   Up 6 seconds (healthy)   0.0.0.0:5332->5432/tcp
```

The container maps host port **5332** to the container's 5432, so it won't
collide with a local Postgres already using 5432.

| Setting | Value |
| --- | --- |
| Database | `devdirectory` |
| User | `devuser` |
| Password | `devpass` |
| Host port | `5332` |

Data persists in the named volume `developer-directory-data`. `docker compose
down` stops the database but keeps the data; `docker compose down -v` also
deletes the volume.

### 2. Run the application

```bash
mvn spring-boot:run
```

Wait for:

```
Tomcat started on port 8080 (http) with context path '/'
Started DeveloperDirectoryApiApplication in 6.485 seconds
```

On first startup Hibernate creates the table (`spring.jpa.hibernate.ddl-auto=update`):

```sql
create table developer (
    id integer generated by default as identity,
    name varchar(255),
    tech_stack varchar(255),
    years_of_experience integer,
    primary key (id)
)
```

Note that the camelCase Java fields map to snake_case columns (`techStack` →
`tech_stack`) via Hibernate's default naming strategy, while the JSON API stays
camelCase.

The API is then available at `http://localhost:8080/api/v1/developers`.

## API Reference

| Method | Path | Success | On missing id | On invalid body |
| --- | --- | --- | --- | --- |
| GET | `/api/v1/developers` | 200 | — | — |
| GET | `/api/v1/developers/{id}` | 200 | 404 | — |
| POST | `/api/v1/developers` | 201 + `Location` | — | 400 |
| PUT | `/api/v1/developers/{id}` | 200 | 404 | 400 |
| DELETE | `/api/v1/developers/{id}` | 204 | 404 | — |

### Validation rules

`POST` and `PUT` bodies are validated before anything reaches the database:

| Field | Rules |
| --- | --- |
| `name` | required, not blank |
| `techStack` | required, not blank |
| `yearsOfExperience` | required, 0–80 |

A violation returns `400 Bad Request` listing every field that failed, so a
client can fix all of them in one round trip rather than one at a time.

## Example Requests

The `curl` commands below are written for **bash** (Linux, macOS, WSL, or Git
Bash on Windows). If you're in Windows PowerShell, see
[Windows PowerShell notes](#windows-powershell-notes) — inline JSON does not
survive PowerShell's argument parsing.

### GET all developers — empty database

```bash
curl -s http://localhost:8080/api/v1/developers
```

```json
[]
```

`200 OK`. An empty collection is a valid result, not a 404.

### POST — create a developer

```bash
curl -i -X POST http://localhost:8080/api/v1/developers \
  -H "Content-Type: application/json" \
  -d '{"name":"Ada Okafor","techStack":"Java, Spring Boot, PostgreSQL","yearsOfExperience":8}'
```

```
HTTP/1.1 201
Location: http://localhost:8080/api/v1/developers/1
Content-Type: application/json
```

```json
{"id":1,"name":"Ada Okafor","techStack":"Java, Spring Boot, PostgreSQL","yearsOfExperience":8}
```

`201 Created` with a `Location` header pointing at the new resource. Omit `id`
from the request body — it's generated by the database.

Two more, to give the later examples something to work with:

```bash
curl -s -X POST http://localhost:8080/api/v1/developers \
  -H "Content-Type: application/json" \
  -d '{"name":"Marcus Lindqvist","techStack":"TypeScript, React, Node.js","yearsOfExperience":5}'
```

```json
{"id":2,"name":"Marcus Lindqvist","techStack":"TypeScript, React, Node.js","yearsOfExperience":5}
```

```bash
curl -s -X POST http://localhost:8080/api/v1/developers \
  -H "Content-Type: application/json" \
  -d '{"name":"Priya Raman","techStack":"Python, Django, AWS","yearsOfExperience":11}'
```

```json
{"id":3,"name":"Priya Raman","techStack":"Python, Django, AWS","yearsOfExperience":11}
```

### GET a developer that doesn't exist

```bash
curl -i http://localhost:8080/api/v1/developers/99
```

```
HTTP/1.1 404
Content-Type: application/json
```

```json
{"error":"Developer with id 99 not found"}
```

A proper `404` with a JSON body, rather than the `500` you'd get from an
unhandled exception. This is handled centrally by `GlobalExceptionHandler`.

### POST — invalid body is rejected

```bash
curl -s -X POST http://localhost:8080/api/v1/developers \
  -H "Content-Type: application/json" \
  -d '{"yearsOfExperience":-5}'
```

```
HTTP/1.1 400
```

```json
{"error":"Validation failed","fields":{"name":"name must not be blank","yearsOfExperience":"yearsOfExperience must be zero or greater","techStack":"techStack must not be blank"}}
```

Nothing is written to the database. All three violations are reported at once.

### PUT — update a developer

```bash
curl -i -X PUT http://localhost:8080/api/v1/developers/2 \
  -H "Content-Type: application/json" \
  -d '{"name":"Marcus Lindqvist","techStack":"TypeScript, React, Node.js, GraphQL","yearsOfExperience":6}'
```

```
HTTP/1.1 200
Content-Type: application/json
```

```json
{"id":2,"name":"Marcus Lindqvist","techStack":"TypeScript, React, Node.js, GraphQL","yearsOfExperience":6}
```

`PUT` is a **full replacement**: send every field. Any field you omit is set to
`null` on the stored record. There is no partial-update (`PATCH`) endpoint.

### PUT — developer that doesn't exist

```bash
curl -i -X PUT http://localhost:8080/api/v1/developers/99 \
  -H "Content-Type: application/json" \
  -d '{"name":"Nobody","techStack":"None","yearsOfExperience":0}'
```

```
HTTP/1.1 404
```

```json
{"error":"Developer with id 99 not found"}
```

Updating a missing developer is a 404 — it will not create one.

### DELETE — remove a developer

```bash
curl -i -X DELETE http://localhost:8080/api/v1/developers/3
```

```
HTTP/1.1 204
```

`204 No Content`, with an empty body.

### DELETE — developer that doesn't exist

```bash
curl -i -X DELETE http://localhost:8080/api/v1/developers/99
```

```
HTTP/1.1 404
```

```json
{"error":"Developer with id 99 not found"}
```

Deleting a missing developer reports 404 rather than silently succeeding.

## Windows PowerShell notes

In PowerShell, bare `curl` is an alias for `Invoke-WebRequest`, which takes
different flags — use `curl.exe` to get real curl. More importantly, **inline
JSON bodies do not work** in PowerShell 5.1: single-quoted JSON, backslash-escaped
`--data-raw`, and the `--%` stop-parsing token all reach curl mangled and produce
`400 Bad Request`. Two approaches that do work:

**Option A — put the body in a file:**

```powershell
'{"name":"Ada Okafor","techStack":"Java, Spring Boot, PostgreSQL","yearsOfExperience":8}' |
  Set-Content -Encoding utf8 ada.json

curl.exe -i -X POST http://localhost:8080/api/v1/developers `
  -H "Content-Type: application/json" -d "@ada.json"
```

**Option B — use PowerShell's native client:**

```powershell
$body = '{"name":"Ada Okafor","techStack":"Java, Spring Boot, PostgreSQL","yearsOfExperience":8}'
Invoke-RestMethod -Uri http://localhost:8080/api/v1/developers `
  -Method Post -ContentType "application/json" -Body $body
```

GET and DELETE have no body and work fine inline:

```powershell
curl.exe -s http://localhost:8080/api/v1/developers
curl.exe -i -X DELETE http://localhost:8080/api/v1/developers/3
```

## Running the tests

```bash
mvn test
```

```
Tests run: 10, Failures: 0, Errors: 0, Skipped: 0 -- DeveloperControllerTest
Tests run: 8,  Failures: 0, Errors: 0, Skipped: 0 -- DeveloperServiceTest
Tests run: 18, Failures: 0, Errors: 0, Skipped: 0
BUILD SUCCESS
```

**The tests do not require Docker or a running database.** `DeveloperServiceTest`
mocks the repository to test business rules in isolation, and
`DeveloperControllerTest` uses `@WebMvcTest` with a mocked service to test the
HTTP layer — status codes, JSON shape, the `Location` header, and validation
responses. That keeps the suite fast and runnable anywhere, including CI.

Covered behaviour includes every 404 path, the `Location` header on create, the
`204` empty body on delete, that a failed update never calls `save`, and that an
invalid body never reaches the service layer at all.

## Configuration

`src/main/resources/application.properties`:

```properties
spring.datasource.url=jdbc:postgresql://localhost:5332/devdirectory
spring.datasource.username=devuser
spring.datasource.password=devpass
spring.jpa.hibernate.ddl-auto=update
spring.jpa.properties.hibernate.dialect=org.hibernate.dialect.PostgreSQLDialect
spring.jpa.show-sql=true
```

`ddl-auto=update` is convenient for development but not appropriate for
production, where a migration tool such as Flyway or Liquibase should own the
schema. Credentials are committed here because this is a local-only development
database; real deployments should supply them via environment variables.

## Known limitations / next steps

Deliberately out of scope for this project, and what I'd add next:

- **DTOs.** Validation constraints currently live on the JPA entity, which
  doubles as the API contract. Separating request/response DTOs from the
  persistence model would stop the database schema and the public API from
  having to change together.
- **Flyway migrations** instead of `ddl-auto=update`.
- **Pagination** on `GET /api/v1/developers` — it returns the entire table,
  which won't hold up past a few thousand rows.
- **Repository integration tests** against a real Postgres via Testcontainers.
  Current tests cover the service and web layers only.
- **Externalised credentials** via environment variables.
- **`PATCH`** for partial updates, since `PUT` requires the full object.

## Troubleshooting

**`Port 8080 was already in use`** — an earlier run is still going. Find and stop it:

```powershell
Get-NetTCPConnection -LocalPort 8080 -State Listen |
  ForEach-Object { Get-Process -Id $_.OwningProcess }
```

Or start on a different port: `mvn spring-boot:run -Dspring-boot.run.arguments=--server.port=8082`

**`Connection to localhost:5332 refused`** — the database isn't running. Start it
with `docker compose up -d` and check `docker compose ps` reports `healthy`.

**`docker : The term 'docker' is not recognized`** — Docker Desktop is installed but
not on this shell's PATH, or isn't running. Open a new terminal after installing,
and make sure Docker Desktop itself has started.

**Table doesn't appear** — Hibernate only creates it when an `@Entity` class is
found. Check the startup log for `create table developer`; with `ddl-auto=update`
the statement is skipped when the schema already matches.
